该仓库采用**分层式错误处理策略**，在不同抽象层级使用不同的错误传播方式：

### 1. 业务逻辑层（Logic）—— 参数校验 + 异常抛出
- `AxisController` 在构造时验证范围合法性，非法参数直接抛出 `ArgumentException`（第33行）
- `AxisJogService` 对步长和方向参数进行严格校验，非法值抛出 `ArgumentNullException` / `ArgumentOutOfRangeException`（第30、46、57行）
- 这些异常属于**编程错误**，由调用方负责捕获或向上冒泡

### 2. 平台适配层（PlatformMotionAdapter）—— try-catch + Debug 日志
- 所有对外部 DLL 的调用均包裹在 `try-catch(Exception ex)` 中（第201、239、277、313、335、357、379行）
- 异常被捕获后通过 `System.Diagnostics.Debug.WriteLine` 输出失败信息，方法返回 `false` 表示失败
- 这种设计确保硬件调用失败不会导致上层崩溃，同时保留调试信息

### 3. 工艺模组层（ProcessModuleBase 派生类）—— MessageBox + InsertAlarm
- `MainControlProcessModule` 和 `PointJumpProcessModule` 在 `Init()`、`LoadSetting()`、`Save()` 等关键路径使用 `try-catch(Exception ex)` 捕获异常
- 异常通过 `MessageBox.Show()` 向用户显示详细错误信息（包含 Message 和 StackTrace）
- 命令解析失败时使用 `InsertAlarm("错误描述")` 记录告警，并返回负数错误码（-1 表示未知命令，-2 表示参数错误）

### 4. 配置持久化层 —— 静默降级
- `MainControlGlobalSetting.cs` 和 `PointJumpGlobalSetting.cs` 在加载/保存配置失败时，捕获异常后回退到默认配置，保证程序可继续运行

### 5. 未覆盖的错误场景
- 未发现统一的错误类型定义、错误码枚举或结构化日志框架
- 没有全局异常处理器（如 `Application.ThreadException`）
- UI 层的 `finally` 块主要用于状态清理（如 `_syncing = false`），而非错误恢复

**约束与约定**：
- 外部依赖（平台DLL）调用必须使用 try-catch 包裹，禁止异常冒泡到上层
- 业务参数校验应抛出标准 .NET 异常（ArgumentException 等）
- 用户可见的错误通过 MessageBox 或 InsertAlarm 呈现，不直接暴露堆栈跟踪给最终用户
